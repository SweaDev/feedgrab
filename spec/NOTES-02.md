# feedgrab 02: implementation notes

Places where the code intentionally differs from `PLAN-02.md`, and judgment calls. Format: `- T<nn>|<topic>: <decision> — <reason>`.

- T41|content: `FeedDescriptor.content` is an optional field on profile v1 (no version bump, no migration), like `permalink` and `structure` in NOTES-01 — it is additive, so v1 profiles stay valid and older readers drop it.
- T42|providers: YouTube embeds use `www.youtube-nocookie.com/embed/<id>` (same player, no tracking cookies until play). Spotify ids keep their type (`episode/<id>`) because the embed URL needs it. A SoundCloud page maps to its `w.soundcloud.com/player/?url=` widget; SoundCloud has no stable public id in the URL.
- T43|media: links count as media only when they are the item's permalink, wrap a thumbnail (`a` with `img`/`picture`) or say `type="application/pdf"`. Any link to a `.pdf` or a provider anywhere in a post (an attachment, a "watch the talk" link) would make text posts PDFs or videos.
- T43|kind: an item with images and at most `IMAGE_MAX_TEXT` (80) characters of text is an image item; 80 keeps captions ("Harbor lights at dusk by Jane") as images while product cards and excerpts (~120+ characters in the v1 fixtures) stay posts. A feed's type is the kind of at least `FEED_KIND_SHARE` (0.8) of its items, else `mixed`. Every v1 fixture reads as a `post` feed.
- T43|title: a permalink whose element is or holds a `<time>`, or whose text is a single word, is not used as the title ("Oct 11", "5h" on status feeds); those items have no title and hosts fall back to their text.
- T43|text: video, audio and PDF items take `text` only from description-like paragraphs (no chrome fallback), so a video card's text is not its duration badge, channel and view count. Paragraphs with `meta`/`author`/`byline`/`date` classes are metadata, not text.
- T43|html: `cleanHtml` is not a sanitizer. It drops scripts, styles, embeds, forms and every attribute but links, sources, alt/title, datetime and sizes, so hosts get compact content HTML; hosts still sanitize before rendering.
- T44|bundle: `content()` pulls the content modules into the IIFE: 94.6 KB → 111.8 KB (limit 120 KB). The item-page parser (v0.8) goes into the separate `feedgrab/page` entry and `describeFeed` (v0.7) must stay small.
- T46|e2e: locally the Chromium and extension e2e projects (14 tests) ran against this machine's preinstalled Chromium build through a temporary config with `executablePath` (the repo pins Playwright 1.64.1, whose expected browser build isn't installed here). Firefox e2e wasn't run locally; the release workflow runs every project.
- T47|detect: `detectFeeds` does not write `content.type` into heuristic proposals (PLAN-02 §3 said it would). A declared single kind sets every item's kind, ads included, so the type must be a user's confirmed choice; hosts read it from `describeFeed` (`type` is the declared one, `detected` what the items' own signals say) and save it after the user confirms. Only an LLM refinement sets `content` on a proposal.
- T47|fields: `suggestFields` skips `html` (it defaults to the whole item); `fieldRuleFor` reads URLs from `src`/`href`/`data`/`content` (a video's `poster` for posters), dates from `datetime`/`content`, and only accepts a link as `mediaUrl` when it points at a media file and as `embedUrl` when it points at a known provider.
- T48|llm: the skeleton now shows `itemprop`, `type`, `datetime`, the `src` host and extension of media tags, and the `href` of links to media files or providers (other links stay hidden, as in v1). Field selectors from the LLM are kept only when they match something in the feed's first item.
- T49|sample: samples keep `src`, `srcset`, `poster` and `data` of media tags (http(s) or relative, at most 300 characters; `data:`/`blob:` dropped) and no longer empty `video`, `audio` and `picture`, so their `source` children stay. This reverses the v0.2 rule that dropped every `src`.
- T50|overlay: `colorScheme: 'auto'` is the default, so the overlay now turns dark on dark-mode pages; `light` keeps the v0.5 look. Feed rows get a type badge computed with `checkDescriptor` per container/item pair (cached), or the descriptor's declared `content.type`.
- T51|bundle: the IIFE is 118.4 KB of 120 KB after `describeFeed` and the overlay changes. The next addition to the core or overlay entry needs a size decision (trim, or raise the budget with the user); `feedgrab/page` stays out of the IIFE.
- T52|page: `describePage` lives in its own entry, `feedgrab/page`, not the core (PLAN-02 had it in core): the IIFE has 1.4 KB left (T51), and only hosts that fetch item pages need it. It trusts JSON-LD over Open Graph/Twitter cards over page elements over the URL's provider, reports an oEmbed endpoint without calling it, and uses the canonical URL as the base for relative links.
- T53|article: `extractArticle` is a separate entry, `feedgrab/article`, so `feedgrab/page` needs no dependency; it statically imports `@mozilla/readability` (optional peer, `>=0.5`) and runs it on `doc.cloneNode(true)`. Readability keeps the page `<title>` as the title when no heading matches it, and prefers a `meta[name=author]` byline over in-text ones.
- T53|fixtures: page fixtures (`tests/fixtures/pages/*.html`) describe one item page each and carry JSON-LD `<script type="application/ld+json">` data blocks (never executed by parseHtml). They have no `.expected.json` and are not part of the feed fixture catalog.
